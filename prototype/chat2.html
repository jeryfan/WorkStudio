高优先级问题

  1. CSRF 来源校验存在确认过的绕过

csrf.py (line 49) 在没有 access cookie 时直接返回，导致来源校验也被跳过。

我实际验证了：携带 Origin: https://evil.example、但没有 access cookie 的登录请求会被接受。登录、注册、刷新令牌、发送验证码等入口都受影响，尤其可能形成 login CSRF。

另外 cookie.py (line 130) 只比较 Origin 的 netloc 和 Host，没有比较协议。HTTPS API 会把同主机的 HTTP Origin 当成同源。

建议：

  • 所有非安全方法先检查 Origin，再判断是否需要 CSRF Token。
  • token_exempt 只豁免 Token，不豁免 Origin。
  • 按完整 origin 比较协议、主机、端口。
  • 不要直接把 CORS 白名单等同于 CSRF/WS 信任白名单，至少禁止凭证模式下的 *。
  1. WSS 鉴权 Cookie 无法正常读取

cookie.py (line 22) 只把 https 视为安全协议，没有包含 wss。

实测 WSS 请求只携带 __Host-access_token 时，get_access_token() 返回 None。因此 auth.py (line 36) 的 WebSocket 鉴权在默认自动判断 Cookie Secure 的生产环境中会失败。

应将 https、wss 都视为安全协议。这个基础设施虽然目前没有路由调用，但按项目规范应保留并修正，不能因未使用而删除。

  1. “撤销全部会话”并没有撤销 access token

account_service.py (line 118) 只删除 Redis 中的 refresh token，而 access JWT 最长仍可继续使用 60 分钟。

因此：

  • 修改密码后，其他设备的 access token 仍然有效。
  • 重置密码后，被盗 access token 仍然有效。
  • revoke_all_sessions() 与其方法名表达的语义不一致。
  • Redis 的 SMEMBERS → DELETE 也不是原子操作，并发刷新可能在撤销过程中生成一个无法再被追踪的新 refresh token。

最简洁可靠的方案是给账号增加 session_version：

  • access JWT 和 refresh token 都携带版本。
  • 修改/重置密码时在数据库事务内递增版本。
  • 每次鉴权、刷新时检查版本。
  • Redis 删除变成清理动作，不再承担核心安全正确性。
  1. DB、Redis、Storage 的成功语义不一致

多个流程先提交一部分状态，再操作另一个系统：

  • file_service.py (line 93)：先保存对象，DB 提交失败后只记录“orphaned”，没有删除对象。
  • file_service.py (line 146)：删除时先删对象，DB 提交失败会留下指向不存在文件的记录。
  • account_service.py (line 433)：密码已提交后，删除验证码或撤销会话失败，接口仍返回 500。
  • 注册可能已经成功创建账号，但消费验证码失败后客户端收到 500，重试又得到“邮箱已存在”。
  • auth.py (line 63) 只有 Redis 撤销成功后才清 Cookie，Redis 故障时用户界面显示退出，但 HttpOnly Cookie 仍然存在。

不需要引入复杂的分布式事务。当前规模下建议：

  • 上传失败时做 storage 补偿删除。
  • 删除文件时优先让 DB 不再引用对象，再异步或尽力清理对象。
  • 密码变更依靠数据库 session_version 保证安全，Redis 清理允许尽力执行。
  • 退出时无论 Redis 是否可用都必须清理浏览器 Cookie。
  • 明确每个流程哪个状态是最终事实源。
  1. 文件与头像流程存在存储泄漏和校验缺口

当前前端头像限制为 5 MB 和 image/*，但后端：

  • 通用上传上限是 15 MB。
  • file_service.py (line 121) 只根据扩展名判断图片。
  • 没有检查文件魔数、实际 MIME、像素尺寸或解压炸弹。
  • 允许 SVG，当前 CSP 只能算缓解措施。
  • 两步“上传文件 → 设置头像”中间失败会产生无人引用的文件。
  • 更换头像时没有删除旧头像，旧公开 URL 会永久有效。
  • 没有用户存储配额，单用户可以持续上传文件。

若当前文件上传只服务头像，建议建立头像专用策略：服务端限制 5 MB、采用实际内容 allowlist、优先禁用 SVG，并在一个业务服务中完成上传、账号更新和旧头像清理。若确实需要通用文件服务，则保留通用上传，但头像绑定时必须再次执行头像专属校验。

  1. 当前 hash/index 改动未完成

model.py (line 12) 新增了 (created_by, hash) 索引，但：

  • hash 从未计算或查询。
  • hashlib 只是未使用导入。
  • 没有对应 Alembic migration。
  • 索引也不是唯一索引，不能真正保证去重。

提交前应二选一：完整实现文件 hash/去重及迁移，或撤掉当前未完成改动。不能保留半套业务方案。

  1. 限流逻辑不是原子的

helper.py (line 25) 的判断和递增是两个独立操作，并发请求可能全部先通过检查，然后一起递增，显著突破限制。

ErrorRateLimiter 的 INCR + EXPIRE 也使用 transaction=False；如果只执行了 INCR，计数器可能没有 TTL。所有安全限流还统一采用 Redis 故障时 fail-open。

建议用单个 Lua 脚本完成清理、计数、写入和过期；并允许不同场景指定故障策略，登录、验证码等安全入口不应和图片预览使用完全相同的 fail-open 策略。

  1. Docker 配置与应用配置严重漂移

我比对了 AppConfig 与 Compose，约 30 个应用配置没有传入容器，包括：

  • Cookie、CORS、Allowed Hosts。
  • Token 有效期和各种锁定时间。
  • 日志配置。
  • MAX_UPLOAD_FILE_SIZE。
  • SMTP_LOCAL_HOSTNAME。
  • 数据库 extras、Redis protocol 等。

docker-compose.yaml (line 1) 只映射了部分变量，而镜像内也没有 .env，因此这些值在 Docker 环境中只能使用默认值。

其他明确问题：

  • Compose 提供了 BROKER_USE_SSL，但 celery_config.py (line 54) 中它是只读计算属性，环境变量完全无效。
  • DEBUG=True/1/TRUE 能被 Pydantic 识别，但 entrypoint.sh (line 28) 只识别字符串 true。
  • REDIS_PORT 同时被当作容器内端口和宿主机映射端口；改为 6380 后，应用会错误连接容器的 6380。
  • make dev 不构建 ideact:latest，新环境或依赖更新后可能直接失败或使用旧镜像。
  • 没有可靠的 migration 启动步骤，/api/health 又不检查数据库表结构。
  • 4 个 Uvicorn worker × (15 pool + 10 overflow) 理论最大 100，已经占满 PostgreSQL 配置上限，没有给保留连接、迁移和管理连接留空间。
  • Nginx 将 X-Forwarded-Proto 强制改为自己的 $scheme。若 TLS 在外部负载均衡器终止，应用会误认为请求是 HTTP，安全 Cookie 和 WSS 都会受影响。

建议的最小改造顺序

  1. 修复 CSRF、Origin 比较、WSS Cookie，并加入 session_version。
  2. 统一密码变更、刷新、注册、退出、文件上传的成功语义和补偿逻辑。
